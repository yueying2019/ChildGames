# 项目实现盘点（2026-09-24）

三玩法休闲小游戏（三消 / 对对消 / 叠叠消），团结引擎 + 微信小游戏方向。
`Assets/Scripts` 共 **127 个 C# 文件**，另有 `Assets/Tests/EditMode` 5 个测试类、`Tools/` 一批 Python 工具脚本。

下面只列**有难度 / 有复杂度**的实现，每项写清「难点 → 采用的开发方式 → 这种方式带来的优点」。

---

## 一、玩法内核

### 1. 三消引擎 `Match3Engine`（1503 行，全项目最重）

**难点**：一次点击会连锁触发消除 → 生成特殊块 → 特殊块再引爆 → 掉落 → 再消除；同时要支持冰块/石头/果冻/笼子等格子类型、三种过关目标、死局检测。如果逻辑写在 View 里，动画和规则会缠成一团。

**做法**：**纯逻辑引擎 + 事件流回放**。
- 引擎只吃坐标、只吐 `Match3ResolveResult`，内含一串 `Match3BoardEvent`（`Swap / SwapRevert / Remove / SpawnSpecial / Move / Spawn / Shuffle / CellHit / Blast` 九种）。
- 引擎内部**不碰任何 GameObject、不跑协程**，`Load(Match3LevelData)` 是纯数据入口。
- `Match3GameView.PlayEventList()` 按事件顺序把结果"演"出来（移动、消除、下落、生成）。

**优点**
- 规则可单测：不进 PlayMode、不建 UI 就能跑完整连锁（`Match3EngineTests`）。
- 动画可换皮：View 怎么演不影响规则，改表现不会把逻辑改坏。
- 统一了"一步操作"的表达：普通消除、道具（`TryPaintSpecial` / `TryClearColorAt`）、结算连击（`ConvertLeftoverMoves` / `DetonateLeftoverSpecials`）走的是同一条事件通道，不用各写一套。

### 2. 对对消寻路 `LianliankanEngine`

**难点**：经典连连看要求通路**最多拐两个弯**，还要能给出路径画线、能判断死局、能重排。

**做法**：**BFS + 方向状态**。`TryFindPath` 用 `DirR/DirC` 四向扩展，状态里带"当前方向 + 已转弯数"，按转弯数做层序遍历，首次到达即最少转弯；路径回写进 `List<Vector2Int>` 供连线特效复用。
配套 `HasMove / EnsureHasMove(洗牌至多 40 次) / RefreshIfStuck / TryHint`。同样是纯数据 `Load(int[,] ids, bool[,] blocked)`。

**优点**：一份实现同时服务「判定」「画线」「提示」「死局重排」四件事，不重复；纯数据入口让 `LianliankanEngineTests` 可以直接构造棋盘验证边界（墙、边界外、同格）。

### 3. 叠叠消棋盘生成 `SheepBoardBuilder`

**难点**：叠叠消是"三张同图进槽即消"，如果图案总数不是 `合成数 × 图案种类数` 的整数倍，或者分布随机，会出现**无解残局**。

**做法**：**结构性保证可解，而不是事后洗牌补救**。
- `unit = ComposeNum × TypeNum`，`total % unit != 0` 时自动调整到合法值。
- `BuildBag()` 按「每种图案发 compose 张」成组造牌袋，再整体 `Shuffle` → 无论怎么洗，每种图案的数量恒为合成数的整数倍。
- 布局走"外形底层 + 边缘多层叠加"，`SheepBoardPlan` 只描述 `GridX/GridY/Layer/IconId`，实例化交给 View。

**优点**：从生成源头消除无解，省掉了运行时的兜底洗牌与"卡死投诉"；关卡参数（`ComposeNum` 3/4 变体、`SlotBonus`、`TimeLimit`、`GoalCount`）只改 `.asset` 就能出新玩法变体，无需改代码。

### 4. 三玩法模板化 + 统一 Session 钩子

**做法**：每个玩法固定 8 件套（Types / Engine / LevelData / LevelCatalog / Session / GameView / TileView / AudioProfile），共性全部上提到 `GameSessionBase`：`ReportResult`（唯一结算出口）、`ComputeStars`（virtual，续关降星统一在基类）、`OfferContinue / TryContinue / AdContinue / ApplyContinue`、`ReportDailyStats`（各玩法重写）。

**优点**：新增玩法只要实现差异部分；星级、续关、降星、广告复活、每日任务这些横切逻辑改一处即全局生效，不会出现"三个玩法三套结算规则"。

## 二、资源与平台

### 5. `AssetHub`：Addressables 封装层（806 行）

**难点**：微信小游戏是 WebGL，**不能用 `WaitForCompletion` 同步等**；远程 bundle 要热更；句柄不释放会内存泄漏；还要显示加载进度。

**做法**
- 全异步：`Load/LoadAll/Preload/PreloadMode` 都走协程，`TryComplete` 只做"已完成则取出"。
- **显式句柄账本**：`TrackKey / TrackLabel → ReleaseKey / ReleaseLabel / ReleaseHandle`，`UnloadMode(mode)` 一次性退场。
- 启动链路 `PrepareStartupRoutine` + CDN 根路径探测（`AddressableCdnPaths`，与微信 DATA_CDN / streamingAssetsPath 对齐）+ 动态调下载并发 + 进度动画平滑。
- **Editor 兜底**：`LoadFromEditor / CollectCached` 让编辑器下不构建 bundle 也能跑通。

**优点**：热更粒度到玩法（`mode_*` 远程组，玩法资源可单独更新，主包不动）；内存边界明确（进玩法加载、退出卸载）；编辑器开发零构建成本。

### 6. 关卡数据三层兜底 + 编辑器工具链

**做法**：`LevelCatalog` 按「Addressables 资源 → 内置 Spec → EditorPrefs」三级取数，任一环缺失都能降级。配套编辑器窗口（`*LevelEditorWindow`）、示例关生成（`*SampleLevelBuilder`）、预制体生成（`*PrefabBuilder`）、Addressables 同步（`LevelAddressableSync` / `AddressableContentBuilder`）。

**优点**：关卡策划不写代码；`mode_*` 远程组里换 `.asset` 就是热更，新关卡不用提审。

### 7. 微信能力反射桥 + 广告强类型桥

**做法**：平台能力用 `WeChatMiniGameBridge` **反射**调用 `WeChatWASM.WX`（SDK 缺失静默降级，不引程序集）；广告用 `WeChatAdBridge` **强类型直连**（`asmdef` 加 `Wx` 引用）+ `AdDirector` 做隐私门禁与点位封装。

**优点**：反射版零依赖、跨项目可分发；广告这种"签名错了就静默不弹"的场景用强类型，编译期就能抓到（原来反射版按 `Show()` 找方法，SDK 只有 2/4 参重载，导致广告永远弹不出且不报错）。

## 三、UI 与表现

### 8. `UIManager`：面板注册表 + 六层 Canvas + 返回栈

**做法**：单 Canvas 六层（Background/Gameplay/Normal/Hud/Popup/Toast）；面板不是硬编码 switch，而是 `PanelRecipe`（Layer / 是否 overlay / 路径 / 构造委托）注册进字典；`_overlayStack` 管遮罩层；返回键走**显式优先级表** `BackPriorities` + `BackStack`（key + priority + `Func<bool>` handle），支持面板自定义返回行为；`HeavyPanels` 进主菜单时协程预热。

**优点**：加面板只加一行注册；返回行为有确定顺序而不是"谁最后开谁先关"的隐式规则；预热消除首次打开商店/选关的卡顿。

### 9. `UITween`：统一补间层（替代 DOTween）

**做法**：静态类 + 隐藏的 DDOL Host 驱动协程，`Move/Scale/Fade/Pop/Shake/Delay/Custom` 统一入口，返回 `TweenHandle`（可 Kill、可 `yield return`），`KillTarget` 按对象批量停；`EaseValue` 是**纯函数**；`SetUnscaled` 支持暂停时仍可播的动画。

**优点**：零依赖（项目无 DOTween）；动画不会互相打架（同一对象重复触发前先 `KillTarget`）；缓动函数可单测；`HintFlash`（15 秒闲置闪烁）就是借 `UITween.Custom` 做的，没额外起 `Update`。

### 10. `ObjectPool` / `ComponentPool`

**做法**：泛型池 + `Stack<T> free` + `HashSet<T> live`，`Take/Return/Adopt/Prewarm/Clear`，`ComponentPool` 包一层负责 `SetActive` 与父节点。

**优点**：`_live` 集合能识别"重复归还""归还非本池对象"，这类静默 bug 在纯 Stack 实现里查不出来。

### 11. UI 点击音效：借 UGUI 自身派发

**做法**：不再每帧 `Input` + `RaycastAll`，而是给节点挂 `UiClickRelay`，在 UGUI 真正派发 click 时回调。

**优点**：零轮询、零射线、零 `new PointerEventData`；UGUI 已经算好的拖动阈值/禁用态/多指判定全部复用，不会出现"滑动列表也响点击音"。

## 四、数据与存档

### 12. `SecurePrefs`：XXTEA 加密 + 明文就地迁移

**做法**：JSON 落盘前过 XXTEA，头部写 `magic(2) + 明文长度(4) + 校验(4)`；读到旧明文 JSON 时自动识别并加密回写。

**优点**：提高篡改门槛的同时**不丢档**（老版本玩家升级后存档自动迁移）；有校验位，被改坏的存档能识别而不是解析成半个对象。

### 13. 数据驱动三件套：每日任务 / 新手引导 / 商店

- **每日任务**：`DailyTaskCatalog`（信号 + 内置条目）× `DailyTaskRepository`（yyyyMMdd 自动重置）× `DailyTaskDirector`（玩法侧唯一上报入口）。
- **新手引导**：`GuideSequence`(SO) + `GuideCatalog` + `GuideDirector.TryShow(mode, key)` + `GuideHighlight`；玩法只上报 key 并提供 targetResolver。
- **商店**：`ShopCatalog` 数据驱动（`ShopItemId` 只追加不插入），`ShopPanel` 自动多一行；图标由菜单 `ShopIconBinder` 用 `AssetDatabase` 按路径绑定（不手算 guid）。

**优点**：加任务/加引导步/加商品都不改逻辑代码；玩法侧与存档、UI 完全解耦（只认 Director）；图标命名即契约（`Assets/UI/<玩法>/<ShopItemId>.png`）。

## 五、工程化

### 14. Python 预制体改写工具链（prefab-first 的代价）

**难点**：项目坚持"结构用预制体、不在代码里 Instantiate 出结构"，但 Unity 编辑器不可脚本化批量改，且本机**没有 C# 编译器**，改完不能编译验证。

**做法**：`Tools/` 下按 `--- !u!<class> &<fileID>` 切块改写 YAML，配套自检（`verify_*.py`）与诊断（`audit_prefab_graph.py` / `dump_children.py` / `clean_dangling_refs.py`）。踩坑固化为 7 条硬约束：
fileID 必须在 SInt64 内、保留 `%YAML/%TAG` 头、新块同时进索引与渲染列表、正则要认 `stripped` 块、guid 不可从 `.meta` 推导（改用编辑器脚本绑定）、悬空判据排除内置 id、报错先看 `Editor.log`。

**优点**：批量改 18 个按钮 / 7 个关卡 / 新增结算按钮这类重复劳动脚本化且**有备份与回滚**；事故复盘成硬约束后同类问题不再复发。

### 15. EditMode 单测（无编译器环境下的质量兜底）

**做法**：给引擎留纯数据入口（`Match3Engine.Load` / `LianliankanEngine.Load(int[,])` / `SheepBoardBuilder` 纯函数），Random 相关内部存取 `Random.state`；已覆盖 Match3Engine / LianliankanEngine / SheepBoardBuilder / UiToolkit / GuideCatalog。

**优点**：本机编译不了也能验证核心规则；写用例前先 grep public 成员，**优先改测试适配公开 API 而不是放开生产访问级别**——这条反过来保护了封装。

### 16. 上架合规层

**做法**：`PrivacyRepository` + `PrivacyPanel` 做隐私门禁（广告初始化必须在同意之后）；`ComplianceCatalog`、`LegalPanel`；棋牌玩法 378Q 已彻底删除并按三条经验收尾（预制体节点跟着删 / 枚举只删不重编号 / Addressables 收尾）。

**优点**：合规是硬性前置条件，做成代码里的显式门禁而不是口头约定，避免"提审被打回才补"。
